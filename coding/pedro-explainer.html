The big ideas

1. A Pose is a spot

p.of(x, y, heading). Inches from the red wall's audience corner, and degrees: 0 faces the blue wall, 90 faces the far side. Pedro always means the center of the robot.

2. A path connects spots

line drives straight. curve bends toward a middle point (the pink one) without driving through it, like a magnet pulling the path.

3. Heading: which way it faces while driving

.constant never turns. .linear turns smoothly from one heading to another. .tangent faces along the path, like a car. .facingPoint keeps the front aimed at a spot.

follow(path)once→ update()every loop→ isBusy()?false = arrived

4. The loop that drives

update() reads the 3 pods, works out where the robot is, and sets the 4 wheel powers. Call it every loop, or the robot stops steering. Add a time limit so a blocked robot can't waste all of AUTO.

Watch out: use Pedro version 3 code only. Most Pedro examples online are version 2. Many names changed in version 3, so that code won't compile. Use pedropathing.com and this example code.

Red and blue: one set of numbers

The blue side of the field is the red side turned halfway around the middle. So the code writes the red spots only, and mirrorAroundPoint(72, 72) spins each one half a turn around the field center for blue: (9, 72) facing 0 becomes (135, 72) facing 180. Press Blue above and watch the same code drive the other side. The drive team picks the alliance during INIT: X for blue, B for red.

Try it in the Virtual Robot

New to the Virtual Robot? Set it up first.

  1. Open the Virtual Robot project in Android Studio and click Git > Pull to get the latest version. Run Main. Pick Mecanum Odometry Bot in the Configuration list.
  2. Place the robot at the start: left-click right next to the red (left) wall, on the line halfway up the field, then right-click to the right of the robot so it faces the blue wall.
  3. Pick Pedro: Auto Launch + Park, press INIT, then START. Watch the telemetry: it shows the same numbers as the black box on this page.
  4. Change the bend. Set bend to p.of(36, 120, 0).Predict first: does the curve swing toward the far side or the audience side? Then run it and check.
  5. Change how it faces. Replace .facingPoint(hive) with .tangent().Predict: which way will the robot face when it reaches the launch spot? Is that good for launching?
  6. Start in the wrong place on purpose. Place the robot one tile closer to the audience, but don't change the code.Predict: where does the robot park? Why? (Hint: what does Pedro believe after setPose(start)?)

Draw your own path

Pedro's own Visualizer lets you draw paths on a field and press Play to watch the robot drive them.

  • Save keeps a project in your browser. Save to computer makes a file you can open again or share.
  • Export > Java code writes Pedro 3 code in the same style as this example: PoseFactory.degrees(), line(...) and curve(...).
  • Nothing goes to the robot directly. Paste the code into an OpMode in Android Studio, then send it to the robot the usual way.

Using the example on your team's robot

Everything that depends on the robot is in two files. The autonomous programs themselves don't change.

  • RobotHardware.java: the motor and servo names. They must match the names in the robot's configuration on the Driver Station.
  • pedro/Constants.java: Pedro's settings for the robot (motor directions, where the odometry pods sit, and the tuning numbers).

Questions you might ask

Why does the robot move in inches if the motors count ticks?

The odometry pods count ticks as they roll. Pedro's settings (in Constants.java) say how many inches one tick is, and where each pod sits on the robot. From that, Pedro turns ticks into a position in inches and a heading.

What happens if I forget to call update()?

Pedro only steers when update() runs. Without it, the wheels keep their last power (or never start) and the robot doesn't follow the path.

Why not just use sleep() and timed driving?

A timed drive goes a different distance every time the battery or the floor changes. Pedro checks the pods every loop and corrects, so the robot ends up at the same spot. And the loop can still react: check the time limit, stop when AUTO ends.

Is the robot really this fast?

No. These motions were recorded in the Virtual Robot simulator, which is quicker than a real robot. The path shape and the order of steps are what to learn here. Time the real robot on a real field.

Where do the field positions come from?

From the BIOBUZZ Competition Manual's field drawings (Section 9). Check them on a real field before trusting them to the inch.

What's pretend in this example

The launcher isn't built yet. robot.launch() only writes a line on the telemetry, the flying balls on this page are pretend, and the launch spot is a guess until the launcher is tested. The drive code, the paths and the telemetry are real: they come from the simulator running this code.
